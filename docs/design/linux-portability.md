# Running Windows VBA on Linux

VBA code is written for Windows: Excel on Windows, Win32, COM, the registry, `C:\` paths. CalcVBA runs the same code on Linux. This note covers:
- which parts of that code are portable as they stand;
- which can be made to behave as on Windows with a shim;
- which only differ in value by machine;
- which need Windows itself.

It proposes run modes and a static check, so that a user can know before running whether a project will behave on Linux as it does in Excel on Windows. A project that will not is either shimmed or rejected with a clear reason.

The per-feature list is `conformance/excel-measurements/vba-library/portability-matrix.tsv`, generated by `make_portability_matrix.py`. It covers every VBA library procedure in `functions.tsv` (VBE7.DLL's type library plus MS-VBAL section 6), plus the statements and language features that reach the host. This note covers the VBA language and library only. The Excel object model (Workbooks, Range, ...) is a host concern: OneCalc and DNA Calc provide it, and it has its own portability story.

## 1. Classes

| Class | Meaning | Count | Examples |
|---|---|---:|---|
| **pure** | The result depends only on the arguments. Portable once the implementation itself does not depend on the platform. | 135 | Left, Mid, Val, CInt, DateAdd, Pmt, Collection, Err |
| **locale** | Depends on regional settings (date order, decimal separator, names, case rules). Portable once the locale is configured for the project, not taken from the Linux host. | 30 | CStr of a Date, CDate("1/2/2026"), Format, FormatNumber, MonthName, StrComp text compare |
| **shim** | Windows behaviour that can be reproduced on Linux by emulation. | 29 | Paths, file attributes, Dir, the registry settings, the ANSI code page, Environ, text-file encoding |
| **host** | The value legitimately depends on the machine and moment; the shape is portable, the value is not. | 12 | Now, Timer, Command, MsgBox/InputBox through the UI host, UserForms (needs a forms host) |
| **windows** | Needs Windows itself. Reject, or replace with a portable class. | 10 | Declare into kernel32/user32, CreateObject of arbitrary COM servers, GetObject, Shell of a Windows command line, SendKeys, AppActivate, AddressOf callbacks |

(The counts are matrix rows: library procedures plus the extra statement and language rows.)

"Pure" is a claim about VBA, not yet about CalcVBA. Today CalcVBA's Sin, Cos, Tan, Atn, Exp, Log and `^` call the platform maths library. Their last bit already differs between Linux and Windows (dc-q6brh.112). Bit-exact means one implementation, the same on every host, matching Excel.

## 2. What CalcVBA does on Linux today

Surveyed 2026-11-18 (file references are in the matrix notes and the survey behind them).

- **Real OS access only in the native policy.** With `HostPolicy::native()` and a profile that matches the build OS (`calcvba-hal/src/model.rs` `host_backed_mode_active`), file, process and clock calls reach the OS. The default policy is deterministic and returns made-up values (in-memory files, an empty CurDir, Shell = 1). The CLI uses the native policy, and `Engine::new` and the differential harness use the default. The capability policy (Safe/Full: `calcvba-hal/src/capability.rs`) decides what is allowed at all. That is a separate axis from portability (section 4).
- **Paths:** Windows paths go to the OS unchanged. A backslash and `C:\` are ordinary filename characters, wildcards in Dir and Kill are case-sensitive, and ChDrive does nothing.
- **Attributes:** only read-only and directory are reported; hidden, system and archive are never set or reported.
- **Settings:** SaveSetting/GetSetting live in memory, on every host, Windows included. Nothing persists between runs.
- **Text and code pages:**
  - Print#/Write# end lines with CRLF (as VBA), but write UTF-8, not ANSI.
  - Chr/Asc/StrConv/String use a hard-coded Windows-1252 table off Windows, and the host code page on Windows.
- **Environ:** names are case-sensitive on Linux. TEMP, TMP, USERPROFILE and APPDATA are absent, and the order of Environ(n) differs from VBA.
- **Declare:** dlopen of `lib<name>.so`, so `kernel32` becomes `libkernel32.so`, which does not exist. Only integer arguments (at most six), no ByRef, no String returns. A Declare into Win32 compiles and fails at run time.
- **COM:** only `Scripting.Dictionary`, as an engine class. Any other CreateObject or GetObject is unsupported off Windows.
- **Shell:** runs `sh -c <text>`, so a Windows command line fails or does something else. SendKeys and AppActivate raise 5.
- **Conditional compilation:** Linux is treated as 64-bit Windows: Win64 = Win32 = VBA7 = True, Mac = False. That is right for code written for Windows Excel.
- **Locale:** none. The conventions are fixed en-US (M/D/YYYY, period decimal) on every host, which is wrong even on Windows for a machine in another region (dc-q6brh.6).

Some of these are bugs on every host, not portability questions. They should be fixed whatever mode is chosen:
- **Open and Name create missing parent folders.** VBA raises 76 instead.
- **Text files are written as UTF-8,** where VBA writes ANSI.
- **Settings don't persist.**
- **Environ(n) order differs** from VBA.
- **The maths functions use the platform library.**

## 3. Modes

Two independent settings decide how a project runs. The first is **policy**, which already exists: what the code may touch (Safe/Full, deterministic or native). The second is **portability**, proposed here: what platform the code is assumed to be written for, and what happens to features that platform has and this host lacks.

| Portability mode | For | pure / locale | shim | host | windows |
|---|---|---|---|---|---|
| **windows-faithful** (default for code from Excel workbooks) | Windows VBA run anywhere, answers as in Excel on Windows | Run; the locale comes from the project (default: the configured Windows machine's settings) | Emulated (section 5) | Run; values are the machine's | Rejected at load, with the reason, unless a portable replacement exists (Dictionary, FileSystemObject, RegExp, emulated kernel32 calls) |
| **strict** | Checking, CI and servers: "will this behave the same?" | Run | Emulated | Flagged in the report; run | Always rejected, even with a replacement, and so is anything unshimmed |
| **native** | Code written for this host (a Linux script) | Run; host locale | Not emulated: real Linux paths and Environ | Run | Rejected where they can't work |

Rejection happens at load, like a compile error in VBE. It names the construct, the line and the reason, rather than failing at run time. This matches the refusal style CalcVBA already uses for constructs Excel refuses. The guarded mode of running VBA under Excel (private desktop, triage before running: dc-vba-triage-policy) is the model: a static pass decides first, then the run.

## 4. The portability report (static check)

A static pass over a project, using the matrix, lists:
- every library call, statement and language feature it uses, with its class;
- every Declare, with its library and whether an emulation exists;
- every CreateObject/GetObject ProgID and early-bound reference, with whether a portable class exists;
- path literals that look like Windows paths (drive letters, UNC, backslashes);
- the verdict: **portable**, **portable with shims** (listed), **host-dependent values** (listed), or **needs Windows** (listed, with lines).

The same pass runs at load in strict and windows-faithful mode, which is where rejections come from. It extends the existing VBA triage (suspect/not) with a portability axis, and can show in OneCalc and in the CLI (`calcvba check --portability`).

## 5. Shims for windows-faithful mode

| Shim | Covers | Design |
|---|---|---|
| **Path mapping** | Open, Kill, Dir, MkDir, ChDir, FileCopy, Name, CurDir, ChDrive, FileLen... | A per-project drive map (`C:` to a root folder; UNC `\\server\share` to a mount; `\` to `/`). CurDir reports the Windows form. Unmapped drives raise 76, as a missing drive does on Windows. |
| **Case-insensitive lookup** | Every path | Resolve each component case-insensitively, as NTFS does. Two entries differing only in case are an error that names both. Creation keeps the case the code used. |
| **Attribute store** | GetAttr, SetAttr, Dir with vbHidden/vbSystem/vbArchive | Extended attributes where the file system has them, otherwise a sidecar. A leading dot counts as hidden for files the code didn't create. |
| **Settings store** | SaveSetting, GetSetting, GetAllSettings, DeleteSetting | A file under `$XDG_CONFIG_HOME/calcvba/settings` keyed as the registry is (`VB and VBA Program Settings\app\section\key`). On Windows, the real registry. |
| **Code page** | Chr, Asc, String, StrConv, Input, Get/Put strings, text files | The project's ANSI code page, default 1252. Text files are written and read in it, not UTF-8. |
| **Environ** | Environ, Environ$ | Case-insensitive names. TEMP/TMP, USERPROFILE, APPDATA, LOCALAPPDATA, COMPUTERNAME, USERNAME, OS and PATHEXT are synthesised from their Linux equivalents, with mapped paths. Environ(n) follows VBA's order. |
| **Locale** | CStr/CDate of dates, Format family, IsNumeric/CDbl of strings, MonthName, text compare | A locale model with the date order, separators, names and case and compare rules, configured per project. The default is the regional settings of the Windows machine whose answers the project was checked against. It is checked against Excel under more than one locale. |
| **Maths** | Sin, Cos, Tan, Atn, Exp, Log, `^` | One implementation reproducing the Excel x64 CRT results, used on every host, Windows included. |
| **kernel32/user32 emulation** | Declare of common calls | A table of emulated entry points with VBA-visible behaviour: GetTickCount, Sleep, QueryPerformanceCounter/Frequency, RtlMoveMemory (CopyMemory), lstrlenW, GetTempPathW, GetUserNameW, GetComputerNameW, MultiByteToWideChar/WideCharToMultiByte. Built from what real projects use: the workbook corpus tells which calls matter. Anything else is rejected. |
| **Portable COM classes** | CreateObject and early-bound references | Scripting.Dictionary exists. Next by corpus frequency: Scripting.FileSystemObject (on the path shim), VBScript.RegExp (the same engine as VBA.RegExp, dc-q6brh.2), ADODB.Stream for text and binary file I/O, MSXML2 for parsing only. Each needs its own Excel-measured probes, like the library. |
| **Shell** | Shell | No general shim: a Windows command line has no Linux meaning. strict mode rejects it; windows-faithful allows a per-project command map for named programs and otherwise rejects. |

## 6. Knowing it's the same

The verification is the same corpora already used against Excel, run on Linux:
- **spec-pass and the vba-library probes,** in windows-faithful mode on Linux, must give Excel's answers line for line. The file-system probes then run on Linux through the path map, instead of being skipped there as they are today. `host`-class lines are compared by shape (type, range, relation), as the probes already print them.
- **The portability report** for the workbook corpus gives the share of real projects that run unchanged, run with shims, or need Windows. That share is the headline number for this work, in the spirit of "refused counts as fail".
- **The differential harness** runs every executor test on both hosts. A difference between Linux and Windows on a `pure` line is a bug, like the Sin last bit today.

## 7. Defaults chosen here (open for review)

- **Default mode:** windows-faithful, for code that comes from an Excel workbook or a .bas/.cls exported from VBE; native only when the project says so.
- **Default drive map:** `C:` maps to a per-project root folder, and no other drives are mapped.
- **Case-insensitive collisions:** an error, not a guess.
- **Default code page and locale:** the measuring machine's settings (code page 1252; en-ZA regional settings until the locale work, dc-7ofm, says otherwise).
- **Conditional compilation:** Win64/Win32/VBA7 True in windows-faithful mode, as today. In native mode the same; there is no "Linux" constant in VBA.
